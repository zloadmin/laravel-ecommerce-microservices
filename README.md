# Laravel E-commerce Microservices

An e-commerce REST API built as a set of independent Laravel services.

## Architecture

| Component | Path | Role |
|---|---|---|
| Gateway | `services/gateway` | Single public entry point: routing, rate limiting, correlation IDs |
| Auth | `services/auth` | Users, registration, login, JWT (RS256), refresh tokens |
| Catalog | `services/catalog` | Products, categories and stock |
| Orders | `services/orders` | Checkout and order lifecycle |
| Cart | `services/cart` | Guest and customer carts in Redis, checkout hand-off to orders |
| Shared package | `packages/shared` | Cross-cutting infrastructure code only (error format, JWT verification, middleware) |

- **Database per service** (PostgreSQL): `auth`, `catalog`, `orders`. No cross-service joins.
- **Sync calls** go over REST; **domain events** go over RabbitMQ.
- Only the gateway is published to the host. Public paths map to services in
  `services/gateway/config/gateway.php` (`/api/v1/products` → catalog, and so on).
- **Authentication:** auth signs short-lived RS256 access tokens with a private key that only it holds.
  The gateway and every service verify them with the public key (`infra/keys`, generated by `make keys`),
  so no service calls auth at request time. Protect a route with the `jwt` and `role:admin` middleware.
- **Events** use a transactional outbox: a service calls `Outbox::record('product.created', [...])` inside the
  same DB transaction as the change, and its `outbox:relay` worker publishes the row to the `ecommerce.events`
  topic exchange (routing key = event type). Delivery is at-least-once, so consumers deduplicate by event id.
  To consume, map patterns to handlers in the service's `config/messaging.php` and run `php artisan events:consume`;
  an event that fails twice is parked in `<service>.events.dlq`. Published outbox rows and deduplication
  records are pruned after 7 days (`MESSAGING_RETENTION_DAYS`) by the relay worker.
- Every error uses one shape: `{"error": {"code", "message", "details"}}`.

## Getting started

Requires Docker with Compose.

```sh
make setup   # env files, image build, composer install, app keys, JWT keys, migrations
make seed    # optional: sample catalog, admin@example.com and customer@example.com (password "password")
make up      # start the stack
curl localhost:8080/api/v1/health
```

| What | Where |
|---|---|
| API (gateway) | http://localhost:8080 |
| RabbitMQ UI | http://localhost:15672 (ecommerce / secret) |
| PostgreSQL | localhost:54320 (ecommerce / secret) |
| Redis | localhost:63790 |

Host ports are set in `.env` (see `.env.example`).

## API

All paths are served by the gateway under `/api/v1`. The full contract is in [`docs/openapi.yaml`](docs/openapi.yaml)
(OpenAPI 3.1); paste it into any OpenAPI viewer to browse it.

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | none | Create a customer account, returns tokens |
| POST | `/auth/login` | none | Returns an access token and a refresh token |
| POST | `/auth/refresh` | refresh token | Rotates the refresh token (single-use) |
| POST | `/auth/logout` | refresh token | Revokes the refresh token |
| GET | `/users/me` | Bearer | Current user profile |
| PATCH | `/users/me` | Bearer | Update name or password |
| GET | `/categories`, `/categories/{id}` | none | List and view categories |
| POST, PATCH, DELETE | `/categories`, `/categories/{id}` | admin | Manage categories |
| GET | `/products` | none | List products (see filters below) |
| GET | `/products/{id-or-slug}` | none | View a product |
| POST, PATCH, DELETE | `/products`, `/products/{id}` | admin | Manage products, including `stock` |
| POST | `/orders` | Bearer | Checkout: `{"items": [{"product_id", "quantity"}]}`, optional `Idempotency-Key` header |
| GET | `/orders`, `/orders/{id}` | Bearer | Own orders (admins: all, filter by `user_id`); filter by `status` |
| POST | `/orders/{id}/cancel` | Bearer | Cancel a pending or confirmed order |
| GET, DELETE | `/cart` | Bearer or `X-Cart-Id` | View or empty the cart |
| POST | `/cart/items` | Bearer or `X-Cart-Id` | Add a product: `{"product_id", "quantity"}` (adds to the existing quantity) |
| PUT, DELETE | `/cart/items/{product_id}` | Bearer or `X-Cart-Id` | Set the quantity, or remove the line |
| POST | `/cart/merge` | Bearer | Move a guest cart into the customer's: `{"guest_cart_id"}` |
| POST | `/cart/checkout` | Bearer | Create an order from the cart, then empty it |

Guests identify their cart with an `X-Cart-Id` header holding a UUID they generate; customers use their token.
A cart stores only product ids and quantities, so it always shows current catalog prices, and it expires
30 days after its last change.

Product list parameters: `q` (name or SKU), `category` (id or slug), `min_price`, `max_price`, `ids[]`,
`sort` (`newest`, `oldest`, `price`, `-price`, `name`, `-name`), `per_page` (max 100) and `cursor`
(from `meta.next_cursor`). Prices are integers in minor units: `{"amount": 129900, "currency": "USD"}`.
Guests and customers see only active products; admins see all.

## Checkout flow

Checkout is a saga across two services; no step calls another service inside a database transaction.

1. `POST /orders`: orders reads current prices from catalog over REST, stores the order as `pending`
   with a copy of each product's name, SKU and price, and records `order.placed`. The response is immediate.
2. Catalog consumes `order.placed` and reserves stock for all lines or none, then publishes
   `stock.reserved` or `stock.rejected`.
3. Orders consumes the answer and moves the order to `confirmed` or `cancelled`
   (`cancellation_reason: insufficient_stock`). Clients poll `GET /orders/{id}` for the outcome.
4. Cancelling publishes `order.cancelled`; catalog puts the reserved stock back.
5. An order still `pending` after 15 minutes (`ORDER_PENDING_TIMEOUT_MINUTES`) is cancelled as `expired`
   by the `orders-scheduler` container, so an outage in catalog cannot leave orders in limbo.

## Events

| Event | Published by | Payload |
|---|---|---|
| `product.created`, `product.updated` | catalog | `id`, `category_id`, `name`, `slug`, `sku`, `price_amount`, `currency`, `is_active` |
| `product.deleted` | catalog | `id` |
| `stock.reserved` | catalog | `order_id` |
| `stock.rejected` | catalog | `order_id`, `reason`, `product_id` |
| `order.placed` | orders | `order_id`, `user_id`, `total_amount`, `currency`, `items[]` (`product_id`, `quantity`, `unit_price_amount`) |
| `order.confirmed` | orders | `order_id`, `user_id` |
| `order.cancelled` | orders | `order_id`, `user_id`, `reason` |

Workers: `catalog-outbox` and `orders-outbox` publish; `catalog-consumer` and `orders-consumer` handle events.
They are long-running PHP processes, so restart them after changing code: `make restart-workers`.

Envelope: `id`, `type`, `source`, `occurred_at`, `correlation_id`, `payload`.

## Common commands

```sh
make test s=gateway   # run one service's tests
make test-all         # shared package and every service
make test-shared
make e2e              # checkout flow against the running stack (needs make seed)
make lint             # code style check for every service
make migrate          # run migrations for all services
make sh s=gateway     # shell into a service container
make logs s=gateway
make pint s=gateway   # format code
make restart-workers  # reload code in the outbox, consumer and scheduler workers
make down
```

## CI

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests: the shared package's tests,
code style and tests for each service in parallel, then the end-to-end checkout test on the full Docker stack.
